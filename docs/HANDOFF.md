# Session Handoff

## Next session: start on sharing — the owner's priority

**The owner wants to start immediately, in the next session, on three sharing features** (asked 2026-09-19): **per-project access** (invite someone to one project with a role, without the organisation's other projects), **view-only share links** to a project or a report (they expire, can be revoked and need no account), and **more than one organisation per account**. None exists today. Sharing is organisation-wide only: an Owner invites someone by email or link with a role (Viewer, Editor, Approver or Owner), the link lasts 7 days, and the person then sees every project in the organisation; an organisation is created only with a new account, at registration or when a platform admin creates a user.

- **The brief is `docs/SHARING_PLAN.md`** (unmanaged, like `docs/PHASE1_DESIGN.md`): what the owner asked for, what exists today (mapped from the code at `199121c`), decisions S1–S15 with proposed defaults, what each feature touches, the test plan and the risks. It now includes the two points from Codex's review of pull request #7, both below.
- **Settle decisions S1–S15 with the owner before writing any code — S2, the spending guard, first.** None is decided until the owner says so; record each in `docs/SHARING_PLAN.md` and in `docs/ROADMAP.md`, where the set is B-16.
- **Order:** fix the fake backend's scoping first, then feature 3 (more organisations), then 2 (share links), then 1 (per-project access, last because it touches every permission check, list and screen) — each its own branch and pull request, with tests written first and seen failing, and the tenancy and role matrices extended before any access check changes.
- **Must not miss:**
  - **S2 — the spending guard.** Every organisation without a budget of its own is held to the $25 default, and B-14 decided there is no cap on the total, with billing (B-12) not built, so free organisation creation multiplies what one account can spend on the deployment's one API key. **The guard must count the organisations an account has created, not those it owns now:** an Owner can promote another member to Owner and then leave, which is allowed while another Owner remains (`backend/routers/organisations.py`), so a cap on owned organisations resets whenever two accounts pass ownership around (Codex's review of pull request #7). Proposed: `MAX_ORGANISATIONS_CREATED_PER_USER`, default 3, counted from a new `created_by` column on `organisations`, platform admins exempt (options (a) to (c) are in the brief).
  - **A public page needs an allow-list of fields.** `_public_product` (`backend/routers/products.py`) returns the whole product row but the SMTP password — `email_settings` and `company_details` included — so a share page must not reuse it.
  - **Bad share tokens (unknown, expired, revoked, malformed) answer 404, never 401:** a 401 makes the frontend client (`frontend/src/lib/api/client.ts`) renew the session and then sign the visitor out.
  - **Live updates are per organisation, and events carry no `product_id`** (`backend/services/events.py`): per-project access must add it and filter per member (S14), or a project-only member learns of every project's results and emails.
  - **A project-only guest needs an organisation context** (feature 1; Codex's review of pull request #7). `/api/auth/me` returns only the user's memberships (`backend/routers/auth.py`), and `AuthProvider` (`frontend/src/lib/auth/AuthProvider.tsx`) picks the organisation for `X-Org-Id` from that list, so `access.membership()` would refuse a guest before any project check ran. The profile must list project grants, each with its project's organisation, and `access.membership()` and the frontend's organisation context must represent guest access without granting membership.
  - **S15 — one permission function in the database, the recommended approach for per-project access** (the owner's colleague's advice). `backend/services/access.py` stays the app's single entry point, and the rule moves into PostgreSQL functions — `effective_role(user_id, product_id)` and `accessible_products(user_id, org_id)` — that every project route and list query uses, so one missed filter can't leak another project's data. The functions get tests of their own against real Postgres. Proposed, like the rest, until the owner decides.
  - **The fake backend scopes weakly — fix it first.** In `frontend/src/test/fakeApi.ts` only `GET /api/products` filters by organisation, and the Playwright bridge (`frontend/e2e/support/fakeBackend.ts`) drops `X-Org-Id`, so browser tests always act in the first organisation and frontend tests can't catch most scoping mistakes. Fixing it also closes pull request #6's open review thread (`fakeApi.ts:709`).

## Warnings — do not learn these the hard way

- **Don't commit, push, merge or post on GitHub without asking the owner, and branch first:** every push to `main` deploys to production. Never `git add -A` without reading the staged diff; never commit `.github/workflows/test-pipeline.yml`.
- **Merge with merge commits, never squash or rebase:** `.gitleaksignore` holds per-commit fingerprints, and rewritten hashes make the secret scan fail on findings already reviewed.
- **Never write a token value anywhere** — not in a file, a document or a commit message. CI runs gitleaks over the full history. **The repository is public:** write local paths with `%LOCALAPPDATA%`, never as an absolute path under the local account.
- **Never run sign-up or registration probes against the live site:** `ADMIN_EMAIL` guards only the first account, and a probe created a real one, which the owner had to delete by hand (T-1). Test registration, new organisations and share links locally.
- **Never run two test suites at once** — not two agents, and never two pytest runs on one test database: that gives deadlocks and foreign-key errors that read like real failures.
- **Never write into OneDrive or the Documents or Desktop folders** — Known Folder Move redirects them into OneDrive; temporary files go in the session scratchpad.
- **Budgets above $25 set before the ceiling existed are kept** — the rule applies to changes. The owner can list any from Railway's Postgres console: `SELECT id, name, monthly_ai_budget_usd FROM organisations WHERE monthly_ai_budget_usd > 25;`
